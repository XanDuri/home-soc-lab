# Scenario 05 — Event Log Clearing (Anti-Forensics) → Severity Tuning

> **MITRE ATT&CK:** [T1070.001 — Indicator Removal: Clear Windows Event Logs](https://attack.mitre.org/techniques/T1070/001/)
> **Tactic:** Defense Evasion
> **Target:** WS01 (192.168.56.20) — Windows 10 Pro
> **Detection stack:** Windows Security/System logs + Wazuh (built-in + custom rule)

---

## 1. Summary

After an intrusion, attackers often try to **cover their tracks** by clearing the
Windows event logs — erasing the record of their brute force, credential dumps,
new accounts, and so on. The irony is that **clearing a log itself generates a
log**: Windows writes a specific, hard-to-suppress event the moment a log is
wiped.

This scenario clears the Security and System logs on WS01 and detects it. It also
shows a **severity-tuning** improvement: Wazuh detects the clearing out of the box
but only at level 5, so a custom rule promotes this high-signal anti-forensics
event to level 12.

---

## 2. Attack (from WS01, as admin)

Clear the two most important logs:

```powershell
# Clears the Security log  -> generates Event ID 1102
wevtutil cl Security

# Clears the System log    -> generates Event ID 104
wevtutil cl System
```

This is destructive — it wipes the event history on the host, which is exactly the
attacker's goal (destroy evidence). In a lab that's fine; the point is the
detection.

## 3. What it looks like in the logs

Clearing a log writes a tell-tale event **into the freshly-cleared log**:

| Event ID | Meaning |
| --- | --- |
| **1102** | The **Security** audit log was cleared |
| **104** | A Windows log (System/Application) was cleared |

These events are generated by the OS at the moment of clearing and include **who**
cleared the log — making log-clearing one of the more reliable attacker signals.

```powershell
Get-WinEvent -LogName Security -MaxEvents 5
# Event ID 1102 — "The audit log was cleared" appears at the top
```

## 4. Detection — built-in rules (level 5) → custom rule (level 12)

### Out of the box

Wazuh already ships rules for log clearing, and they fired immediately:

| Wazuh rule | Description | Level |
| --- | --- | --- |
| **63103** | The audit log was cleared (Event 1102) | 5 |
| **63104** | A Windows log file was cleared (Event 104) | 5 |

> 📸 **SCREENSHOT 3 — `screenshots/03-wazuh-builtin-level5.png`**
> The built-in alerts 63103 and 63104 firing on the cleared logs — but only at
> **level 5** (informational).

### The problem — and the fix

Log clearing is a **high-signal, rarely-legitimate** event, but the built-in rules
report it at level 5 — low enough to be buried among routine informational alerts.
A custom rule inherits from both built-in rules and promotes the event to
**level 12**, mapped to MITRE. Stored in
[`/wazuh-rules/local_rules.xml`](../../wazuh-rules/local_rules.xml):

```xml
<rule id="100103" level="12">
  <if_sid>63103,63104</if_sid>
  <description>Possible anti-forensics: Windows event log was cleared</description>
  <mitre>
    <id>T1070.001</id>
  </mitre>
</rule>
```

> 📸 **SCREENSHOT 4 — `screenshots/04-custom-rule-100103.png`**
> The custom rule 100103 in `local_rules.xml`.

After reloading the manager and clearing the logs again, the custom rule fired at
level 12:

```
Rule 100103 (level 12):
Possible anti-forensics: Windows event log was cleared
```

> 📸 **SCREENSHOT 5 — `screenshots/05-wazuh-alert-100103.png`**
> The custom alert 100103 (level 12) for Security and System log clearing.

This is a clean example of **severity tuning**: the detection existed, but making
it actionable (promoting it above the noise floor) is part of the SOC's job.

## 5. Incident report (SOC L1 view)

| Field | Value |
| --- | --- |
| **Incident ID** | INC-2026-005 |
| **Severity** | High |
| **Detection time** | 2026-07-04 ~12:11 UTC |
| **Affected asset** | WS01 (192.168.56.20) |
| **Actor** | CORP\Administrator (admin session) |
| **Action** | Security log (1102) and System log (104) cleared |
| **Triggered rules** | 100103 (custom, level 12); 63103 / 63104 (built-in, level 5) |
| **Indicators (IoCs)** | Event 1102 (Security cleared); Event 104 (System cleared) |

**What happened:** The Security and System event logs on WS01 were cleared. This
is a classic anti-forensics move to destroy evidence of prior activity — it almost
never has a legitimate cause and strongly implies an active intrusion.

**Recommended actions (L1 → L2):**

1. **Treat WS01 as compromised** — log clearing implies the attacker had (at least)
   admin rights and something to hide.
2. **Pivot to the SIEM copy of the logs.** Because Wazuh forwards events as they
   happen, the pre-clearing history is preserved server-side even though the local
   logs are gone — a key reason central logging matters.
3. Identify what the attacker did **before** clearing (correlate earlier alerts on
   this host — brute force, credential dumping, etc.).
4. Investigate how admin rights were obtained.
5. Escalate to L2 / IR.

---

## 6. Lessons learned (defender's view)

- **Central logging defeats log clearing.** Forwarding events to a SIEM in real
  time means wiping the local log no longer destroys the evidence — the server
  already has it. This scenario is the best argument for a SIEM.
- **Log clearing is high-signal — alert loudly.** There's rarely a legitimate
  reason; promote it above informational noise (as the custom rule does).
- **Correlate around the clear.** Log clearing is an endgame move — look at what
  happened on the host just before it.
- **Protect the logs.** Restrict who can clear logs, and consider WEF (Windows
  Event Forwarding) / immutable log storage so history can't be erased locally.
